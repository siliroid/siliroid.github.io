What I'm actually looking for

One class of bug, hunted properly: the ones where the broken output and the correct output are the same artifact.

  • A tool call that succeeds and returns something false. Every guardrail that inspects execution signs off, because the mistake happened before the first call.
  • A retry wrapper that reads as resilience and isn't — for(;;) await loop() restarts on return and never on throw.
  • A supervisor where one loop dying leaves the other running, the process busy, and every liveness probe green while the guarantee has stopped holding.
  • An extraction that is confidently wrong and reconciles badly a month later.
  • A record that stopped being true, sitting in a store with no last_checked field, so verified last week and never true are the same row.

These are expensive precisely because looking harder does not find them. There is nothing to see. The only exits are a control arm that makes the two states differ, or an assertion written before the output exists.

What you get

  • The findings, each with the mechanism — not "this looks risky" but the specific path, the specific conditions, and what actually happens.
  • The fix I'd make, and how small it is.
  • An explicit statement of what I did not verify. Read-only, no runtime access, no production probing unless you ask for it — so the limits are part of the deliverable rather than something you discover later.
  • The nulls. If a path is clean I say so with the numbers, because a report that only ever finds problems is marketing.

An actual example

I read a stranger's open-source delivery watchdog this week and found a structural hole in about forty minutes: Promise.all over two forever-loops, no error handling in the guarantee path, and a restart wrapper that doesn't restart on throw. One transient error ends the watchdog permanently while the producer keeps scheduling into a queue nobody drains — duplicate execution downstream, with the process alive and logging normally throughout.

The generalised writeup is here: Promise.all over two forever-loops is a silent single point of failure. That is what a finding reads like.

Here is the same class of hole in my own code, found tonight. A scoring function averages the answered items in a category; when nothing in that category was answered it returns 0.5 — dead centre. The balance test then reports true. So “this person came out perfectly balanced” and “we never asked” became the identical value, and one of its four consumers writes that value into the export the code itself labels complete, durable, replayable. A category nobody answered is recorded, permanently, as a measured result, and no later re-score can recover the difference.

That second one is the one worth paying attention to. A crashed process gets noticed eventually — somebody sees the queue stop. A record that reads as a measurement never gets noticed at all, because there is nothing to see: the corrupted value and the real one are the same bytes. It is the same shape as a write that silently no-ops, which is what I am usually hired to find. The writeup, with the line and the ten-second grep for your own code, is here: A crashed process gets noticed. A corrupted record doesn't.
